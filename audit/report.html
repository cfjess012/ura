Structurally strong, production-blocked on one thing. This is an unusually well-disciplined codebase — strict types with almost no escape hatches, invariants enforced in the schema rather than in UI code, pure logic genuinely separated from executors, and a governance log that records why decisions were made.

The gate chain is real and it passes: 740 unit + 51 integration + 72 agent + 73 end-to-end tests, all executed in this session, all green. Most audits of a codebase this size find correctness problems. This one does not.

What it finds instead is a gap between what the specification says is enforced and what is actually enforced, and one hard production blocker.

The five that matter

  1. There is no authentication. The identity cookie is unsigned and httpOnly: false. Anyone can become any persona, including the administrator. Every downstream authority check is correct and keys off an identity nobody proved. Acknowledged in §12 and scheduled for Phase 3 — fine for a sandbox, and the single thing standing between the deploy and production.
  2. 14 high-severity dependency advisories, most requiring Next ≥ 15.5.x — which conflicts with the deliberate, measured 15.3 pin (G-58). A real trade-off, not an oversight, but it needs a decision.
  3. CI never runs the end-to-end suite. The tier that proves journeys work runs only on a developer's laptop.
  4. No linter and no formatter exist anywhere, under a specification that opens with a clean-code charter.
  5. §11 asserts mechanical enforcement that does not exist. "File budgets enforced mechanically (≤400 / hard 800)" and "an unused-export gate keeps it dead" are present tense. Neither gate exists, and assistant.css is 4,772 lines — six times the stated hard ceiling.

02 The specification

This spec is leaner than its 132 KB suggests: §13 (the governance log) and the §20 register are append-only by design, and the repo's own length guard already excludes them for that reason. One bloat finding only — the §11 / §20 contradiction, recorded as F-05 below. Everything else in §11 is enforced by a real test.

F-01CriticalSecurity

src/lib/current-person.ts:24 · src/app/actions.ts:642, 666

Evidencejar.set(PERSON_COOKIE, id, {path:'/', sameSite:'lax', httpOnly:false}) — no signature, no secure flag. currentPerson() trusts the value if it names any sign-in persona.

07 Remediation plan

Ordered by severity and dependency, not by discovery.

Now — before anything ships to production

  1. F-01 authentication. Signed session cookie at minimum; SSO at the edge properly. Nothing else on this list is close in consequence. Until it lands, treat any deployment as sandbox-only with synthetic data.
  2. F-02 dependency advisories. Decide the Next question explicitly — re-test 15.5.x (G-58's measurement may be stale by now), or record the acceptance with an expiry.
  3. F-08 the expired banner. One-line deletion; it is instructing sessions to skip testing right now.

Next — before the next slice is called done

  1. F-03 end-to-end in CI. Needs only a Postgres service and one env var.
  2. F-04 linter and formatter, wired into CI alongside typecheck.
  3. F-06 / F-09 delete the dead code. One commit; git remembers.
  4. F-05 resolve the contradiction. Build the file-budget test, or move §11 to future tense. Building it is the better trade: the repo's own hard-won rule is that what nobody writes down mechanically is invisible to the suite and the verifier — and there is already a file six times over the cap to prove it.

Later — with S10

  1. F-07 traceability. Cite requirement IDs in tests and assert the register is fully cited. That turns it into something a machine can check.
  2. F-10 LICENSE and CONTRIBUTING.md.
  3. NFR-4 performance re-proof, already scheduled.

08 Not verified in this audit

Silence about gaps reads as coverage, so:

  • The AWS deployment. No stack created, no image built. deploy/READINESS.md already says so: "ready to deploy, never deployed."
  • Bedrock. The provider seam is proven against an API-compatible local model — which proves the seam, not the model grant.
  • NFR-4 recompute performance. Not measured. Scheduled for S10.
  • AI grounding. Gates and abstention are tested against fabricated replies (72 tests). No live model output was taken and its verbatim quote checked against a source document.
  • Colour contrast and screen-reader announcement. Markup checked (role, aria-*); nothing measured with a contrast tool or heard with a reader.
  • Migrations individually. All 30 are applied in order by the integration suite on every run — stronger evidence than reading them — but none was read line by line.
  • Instrument content. Structure checked; the 51 control objectives and 26 severity questions were not reviewed for correctness. That is an instrument review, not an engineering audit.
  • A real secrets scanner. gitleaks/trufflehog were not installed. The screen used was pattern-based over the working tree plus git log -S over full history.
  • pnpm walk:demo. Not run: it drops and rebuilds the development database, which would have destroyed the owner's working data.

09 Questions for the owner

  3. Does the demo-readiness gate survive the pivot to production? It is the only mechanism in the repo that asks whether a person has actually used a feature before it is called done, and it is currently worded for a demo.
