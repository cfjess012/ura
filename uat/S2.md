### FR-3 — One gate per category; No closes the category entirely

- **What was done:** Walked all eleven gates in the browser, answering Yes on some and No on others, then reloaded cold.
- **What was observed:** Each risk area is its own screen with one Yes/No question. Answering "No, it doesn't" on Solution Architecture struck that entry through in the rail and labelled it "Not applicable", while remaining clickable so the person can change their mind. Eleven categories, eleven unique question ids, each with plain-language help beneath the question text.
- **Result:** pass
- **Evidence:** `e2e/gates.spec.ts` answers No on Systems & apps and asserts the rail shows "Not applicable" both immediately and after a cold reload on a fresh page. `test/unit/instrument.test.ts` asserts eleven categories with unique keys and question ids.

### FR-22 — An intake answer that duplicates a Tier-1 gate pre-answers that gate — visibly, with its reason, and changeable

- **What was done:** Completed intake naming a vendor and answering Yes to AI, then opened the gates.
- **What was observed:** Third-Party arrived pre-answered with "Answered from your intake — we've marked this **Yes** because you named a vendor at intake. Change it if that's not right", and the Yes option carried `aria-pressed="true"`. Four of eleven gates pre-fill (third-party, systems, AI, data). Answering "I'm not sure" to the AI question pre-fills nothing — uncertainty is not laundered into a confident gate answer.
- **Result:** pass
- **Evidence:** `e2e/gates.spec.ts` asserts the banner text, the reason, and the pressed state, then changes the answer. `test/unit/instrument.test.ts` asserts `prefillFor` returns null for "I'm not sure" and for an empty intake (positive evidence only).

### NFR-1 — Evidence and export records are insert-only (schema CHECKs, not convention)

- **What was done:** Attacked the database directly, bypassing every product code path: attempted UPDATE and DELETE on an `answers` row, and attempted inserts violating the source and confirmation constraints.
- **What was observed:** UPDATE and DELETE both raise `answers are insert-only (SPEC NFR-1): record a new answer instead of changing …`. An unknown source is rejected by `answers_source_known`; a `person` answer that is not confirmed is rejected by `answers_person_is_confirmed`. Two answers to the same question both survive, and the newest is read as current.
- **Result:** pass
- **Evidence:** `test/integration/invariants.test.ts` — four assertions against real SQL on in-process Postgres, with no application code in the path.

### NFR-8 — Instrument entirely as versioned seed data; zero hardcoded content

- **What was done:** Moved all eleven gates into `src/data/instrument/gates.json`, imported at build time, validated on load; seeded and activated as a version row.
- **What was observed:** No gate text exists in any component. A malformed instrument throws on import with the specific problems listed. Editing the file requires a new version string, because the activated one is immutable.
- **Result:** pass
- **Evidence:** `test/unit/instrument.test.ts` validates structure, uniqueness, help-text presence and pre-fill reasons; the wording rewrite mid-slice required a version bump to `2026-08-21.2` and a re-seed, which is the mechanism working.

### NFR-11 — Instrument versions immutable once activated; answers pin their version

- **What was done:** Attempted to modify an activated `instrument_versions` row directly in Postgres; also modified a draft row.
- **What was observed:** The activated row raises `instrument version tier1-gates/test.1 is activated and immutable (SPEC NFR-11): create a new version`. A draft row still accepts activation. Every answer row carries a non-null `instrument_version_id`.
- **Result:** fail
- **Corrected 2026-08-21, after independent verification:** "immutable" was tested for UPDATE only. The guard was a `before update` trigger, so `delete from instrument_versions` walked straight past it — and deleting the version an assessment pins is worse than editing it, because the answers survive pointing at questions nobody can reproduce. Closed by `drizzle/0007_activated_versions_undeletable.sql`; both verbs are now covered by tests, including that a *draft* version may still be deleted.
- **Follow-up (done 2026-08-21):** migration 0007 adds a `before delete` guard; `test/integration/invariants.test.ts` now covers UPDATE-refused, DELETE-refused, draft-deletable and draft-activatable.
- **Evidence:** `test/integration/invariants.test.ts` — four assertions against real SQL, all attacking the database directly rather than through the product.
