# UAT — S13 · Debts first

**Done when:** Gate chain green; an expired acceptance reads open in the queue, the review and the package alike; an overdue fix is named in all three.

This slice owns no new requirement. It fixes seven defects the 2026-09-02
evaluation found, each under the requirement it broke (G-76). One row per
defect, with what was done and what was actually observed.

### (a) The queue's open-finding SQL — under FR-18 / FR-16

- **What was done:** Read `projectStore().awaitingReview()` beside `findingIsOpen()`. The SQL treated *any* disposition row as a settlement (`left join dispositions … where d.id is null`), so an acceptance past its expiry was invisible to the queue and the bell while the review, the report and the packaging gate all showed it open. Rewrote the three subqueries to take the **newest** settlement per finding (`order by d.resolved_at desc limit 1`) and to state the one rule in SQL: open when unsettled, or when the settlement is a risk acceptance whose expiry is null or past. Ran the real store against real SQL on PGlite by handing the in-memory database to `getDb()`'s global before importing the store.
- **What was observed:** With two findings — one acceptance lapsed yesterday, one live for 90 days — `openGaps` names the lapsed one and not the live one. A finding settled twice (a lapsed acceptance, then a remediation) reads as settled: the newest row decides. The existing architecture test could not see this defect because the SQL never calls `dispositionsFor(`; a second rule now holds any raw SQL that reads `dispositions d` to both the expiry clause and the newest-row ordering.
- **Result:** pass
- **Evidence:** `test/integration/queue.test.ts` (3 tests, real SQL); `test/unit/architecture.test.ts` — "raw SQL that reads dispositions states the open rule findingIsOpen states".

### (b) The hand-off thread cap — under FR-36

- **What was done:** `depthOf(node, depth = 0)` ignored its argument and returned the default, so `MAX_DEPTH = 4` was declared and never reached. Rewrote it to walk the chain of parents, and made `replyToHandoff` refuse a reply that would sit at or past the cap with the sentence the panel already offers — post it to the whole thread instead. The reply stays on screen (§25).
- **What was observed:** A chain of five replies reports depths 0…5; a reply to a missing parent stops at 1 rather than throwing. The refusal is an expected failure with no support reference, as §25 requires for a rule doing its job.
- **Result:** pass
- **Evidence:** `test/unit/handoff.test.ts` — "the staircase rule is real (S13)" (2 tests).

### (c) An approval owes a note, at the database — under FR-16

## Findings

- **The one-rule design was defeated by the one reader it could not reach.** `findingIsOpen`'s docstring said the queue asked it; the queue is raw SQL and never could. The structural test that guarded the rule only scanned for `dispositionsFor(` callers. Severity: high (a lapsed acceptance disappeared from the reviewer's list). Follow-up: none owed — both the SQL and the test now state the rule; S20's exception register will read the same counts.
- **A CHECK added to a table with history has to be `NOT VALID`.** Pre-2026-08-25 approvals carry empty notes and are evidence. Recorded here so the next constraint on an evidence table is written the same way.
- **The queue's "Settle findings" door opened for a gap, an enhancement or a violation, not for an overdue fix** — found while reading the row for S15; the door now opens for `overdue` too, so the standing item and the button agree.
- **The dossier shows an overdue fix only where a settlement renders.** The domain dossier's recommendations table gained the chip; the assessment-wide leftovers section does not show settlements at all and so shows nothing here either. Severity: low. Follow-up: S20's history and exception views.
