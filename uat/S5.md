## Findings

**One acceptance criterion was wrong, not unmet.** §19 required that "a
capture-marked answer never changes the accumulated set", which contradicts
FR-10 and §3.3 — both say option selections may require objectives directly.
The rule §3.1.6 actually draws is narrower: a capture answer never affects
accumulation *thresholds*. Criterion corrected and tested (G-57). Writing a
test for the criterion as written would have encoded a contradiction into
the suite.

**FR-11 was genuinely incomplete.** The requirement names three things and
the panel showed one. Found by reading the requirement against the screen
during the S6 pre-flight, which is what a pre-flight is for — S5 had never
been marked done, and starting Tier 3 on top of it would have buried this.

**A tooling defect found on the way.** `uat:new` read §17's columns by
position, so the Status column added on 2026-08-23 shifted them silently and
this skeleton's first draft carried the Builds prose as its requirement row.
It now finds columns by header name and throws if one is missing.

## Agentic opportunity

The ledger is the natural home for the contradiction-finding registered in
§22.1: it already holds every active path, every severity and every
objective in one recomputed view, which is exactly the input a consistency
pass needs. An agent could say "you answered Access & Output Audience as
internal-only, but the description says customer-facing" — naming both sides
and quoting them, never resolving. Nothing in this slice forecloses it: the
ledger is derived from answers on every render, so a reader of that state
needs no new storage and no new evaluator.

Guardrails it would need: it flags, never edits; both sides quoted verbatim
from what the person wrote; and the deterministic half must stand alone, so
a contradiction between two structured answers is caught with no model
available.
