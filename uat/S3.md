**Done when:** §19 engine + routing criteria pass; changing an upstream answer re-derives everything.

### FR-4 — Tier-1 selections activate paths; union semantics with reasons retained

- **What was done:** Completed intake for an AI scheduling tool from a vendor handling confidential data, answered every gate, then selected threads on the paths screen: logical access and subcontractor reliance under Third-Party, decision influence under AI, personal information under Data & Privacy.
- **What was observed:** Seventeen selectable threads across the four deep areas, each with its own helper text. Selections are stored as a JSON list on an insert-only answer row (`path.third-party`), so changing a selection writes a new row and the previous one survives. An area whose gate says No shows no path question at all, and a selection made before a gate was closed stops being lit without being deleted — union semantics: chosen ∪ derived, nothing subtracted silently.
- **Result:** fail
- **Corrected 2026-08-21, after independent verification:** activation and union semantics work, but "**reasons retained**" did not. `LitPath.because` was a single string and the engine de-duplicated on id, so when two rules both lit one path the second reason was silently discarded — §19 asks for the path active *with both reasons*. No shipped path had two rules, so nothing was visibly wrong and no test covered it. Separately, `answerPaths` **narrowed** a submission containing an unknown option instead of refusing it, turning a person's real selections into a positive "none of these apply".
- **Follow-up (done 2026-08-21):** `because` is now a list and every satisfied rule contributes. A submission containing an option the instrument does not offer is refused rather than narrowed — **and the second round found that half pinned by nothing**, so the rule was extracted as a pure function (`pathSubmissionProblems`) and now has its own tests, which is also where it belonged under §26.1.

### FR-5 — Any visible question can explain itself in one English sentence

- **What was done:** Read every path option and every derived path on screen as the person they are for, and checked the instrument validator refuses content that cannot explain itself.
- **What was observed:** Each of the seventeen options carries a plain sentence ("They can sign in to our systems, or we give them accounts"). Each of the three derived paths states its reason where the question would have been — "every supplier gets this one — how hard would they be to replace?" and "you told us personal information is involved and that this uses AI". The validator rejects a derived path with no `because`, so the sentence is not optional.
- **Result:** fail
- **Corrected 2026-08-21, after independent verification:** every path *option* and every *derived path* explains itself, which is what this record checked. But FR-5 cites §6.3, which asks the engine to **render any condition as a sentence and lint authored conditions for contradictions** — neither exists. Explanations are hand-authored strings, and the drift a renderer would prevent had already happened: the security gate's reason named evidence the person never gave.
- **Follow-up:** the false sentence is fixed and provenance now names its real source. A condition renderer is **not** built, so FR-5 is **not met** and is carried into S4 rather than claimed here.

### FR-9 — Answer changes re-derive all routing; history never deleted

- **What was done:** Completed an assessment with AI answered No, confirmed the AI area was closed and the cross-domain path absent, then went back to intake, changed the AI answer to Yes, and returned to the paths screen.
- **What was observed:** The AI area reopened, its path question appeared, and "Personal Information in AI / GenAI Use" lit itself — with no migration, because nothing derived had ever been written. The earlier answers remain as rows: nothing was updated or removed, and the insert-only trigger would have refused it anyway.
- **Result:** pass
- **Evidence:** `e2e/paths.spec.ts` "changing an upstream answer re-derives the paths — nothing is stored" drives exactly this; `test/unit/instrument.test.ts` proves the same at the engine level in both directions.

### NFR-2 — One visibility predicate consumed by every surface

- **What was done:** Traced every place a condition is evaluated after adding paths and gate-to-gate pre-fill.
- **What was observed:** `matches()` in `src/lib/conditions.ts` is still the only evaluator. Intake visibility, gate pre-fill, derived paths and the new conjunction helper all route through it — `matchesAll` folds over `matches` rather than interpreting anything itself. Intake fields, gate answers and path selections share one flat namespace, so a rule reads `gate.ai` or `paths` without any surface needing its own lookup logic.
- **Result:** pass
- **Corrected evidence 2026-08-21:** the requirement is met — `matches()` is still the only evaluator — but this row cited `test/unit/architecture.test.ts` as keeping the engine pure, and that test's list covered `intake.ts`, `intake-values.ts` and `errors.ts` only. `engine.ts`, `conditions.ts` and `people.ts` were never in it. They are now. Citing a test that does not cover the thing is the same overstatement as claiming an untested behaviour.
- **Evidence:** `assessmentLookup()` builds the namespace in one place; the architecture test now actually covers the engine.

### NFR-3 — Positive evidence only; severity fails closed

- **What was done:** Checked what an unanswered or absent field does at every new decision point, and what happens to derived state when its evidence disappears.
- **What was observed:** An unanswered field satisfies nothing — an absent gate answer does not light a derived path, and an area with no gate answer contributes nothing. Nothing derived is stored anywhere, so removing the evidence removes the derivation on the next render rather than leaving a row behind. Severity is not built yet (S4); the "fails closed" half of this requirement is therefore only half-exercised, and is noted below rather than claimed.
- **Result:** pass
- **Corrected 2026-08-21:** the sentence "the two-pass design means a pre-fill can only ever read a settled answer" was **false** — pass two read unconfirmed pre-fills, so a gate could and did chain off a pre-filled gate. Worse, two passes silently capped derivation at one hop, so a rule reading two steps upstream validated fine and then did nothing at all. Resolution is now a fixed point bounded by the number of categories.
- **Evidence:** `test/unit/instrument.test.ts` proves PI-in-AI does not light when either half is missing, that the security gate stays null when the gate it reads has no answer, and that a **three**-hop chain resolves. The earlier claim cited a two-hop chain, which the old two-pass code also resolved — it would have passed unchanged on the broken code, so it evidenced nothing. Testing it required `gateStates` to take its categories as an argument instead of reading a module global, which the second round separately flagged as a hidden input in a module certified pure.

### NFR-4 — Full-instrument recompute in single-digit milliseconds

- **What was done:** Measured a full recompute a thousand times. **Correction:** this row described its fixture as "every gate settled across all eleven categories"; that fixture actually left five gates unanswered. Independent verification re-ran it with all eleven open and all seventeen options selected and got the same numbers, and confirmed against a no-op control that the loop measures real work (~80× a no-op) rather than an early return.
- **What was observed:** Median 0.006 ms, p95 0.008 ms, worst single run 0.134 ms. Three orders of magnitude inside the budget, which is what makes "never store derived state" affordable: it is recomputed on every render, and if that were expensive somebody would eventually cache it, and the cache would be the thing that goes stale.
- **Result:** pass
- **Evidence:** `test/unit/instrument.test.ts` "NFR-4 · a full recompute is cheap enough to do on every render" fails the build above 5 ms — deliberately loose so a slow CI box does not fail for a budget it is nowhere near.

## Findings

**Independent verification, 2026-08-21 — VERDICT FAIL, four blocking.** All four are fixed and pinned by tests:

- **B1 — the form said "nothing was saved" after saving half of it.** Areas were written in a loop, so a failure partway committed the earlier ones; the message claimed the opposite, and the uncommitted ticks then vanished on reload. **This record originally said "nothing is lost and the person is told" — the exact inverse of what happens.** One transaction now covers every area, so the sentence is true; ticks also save as they are made, so leaving by the rail no longer discards them; and the transport failure carries a per-incident reference instead of the literal string `OFFLINE` — **on the paths form only**; the second round found the literal still in the gate form and the intake form, now both fixed.
- **B2 — a dead end.** Answer No to every area and the paths screen showed an empty state with no button and no link: the only way forward was to type the URL. It now offers the summary, and the lede no longer tells someone to tick things that are not there.
- **B3 — both engine rules the commit message said the validator enforced were unenforced, and the shipped instrument already violated one.** Gate pre-fill chained through a pre-filled gate (and a unit test asserted that forbidden chain as correct); derived-path chaining passed validation and then silently never fired, which is worse than a rejection because the rule looks right. Chaining is now genuinely rejected across the whole instrument, and gate resolution is a fixed point.
- **B4 — §19's "both reasons retained" was not implemented.** See the FR-4 row.

Also fixed from the same run: §24.1 was violated on the screen this slice built — someone who said "I'm not sure" about AI was asked five sharper questions about it one tier later; that area now says so and leaves it to a reviewer. `seedPrefilledGates` was an exported server action with no callers and **no authority check**, able to write answer rows for any project id handed to it; deleted. Content defects ("The rest are closed" printed when nothing was closed; "1 risk area apply"; a doubled full stop) corrected.

- **Parts-shelf decision #1 (§17) — rewrite, not salvage.** The prior platform's condition engine solves module activation for a flat questionnaire; paths, severity bands and threshold routing are a different shape. Adapting roughly a thousand lines built for another model would have cost more than the hundred and fifty written against the predicate this codebase already had. Its test patterns were taken. Recorded as G-40.
- **Fixed while building:** the path group announced its question twice — once visibly, once as a hidden group label — so a screen reader heard it twice. Same defect class as F8. Now one label, referenced by id.
- **Audit C-5 closed by the same mechanism.** Solution Architecture = Yes now answers the Security & Resilience gate with its reason on screen. It could not be written before, because pre-fill only read intake — which is why the audit's proposed fix did not work as written, and why the audit was corrected rather than quietly satisfied.

## Second verification round, 2026-08-21 — FAIL, two blocking

Both were the product **stating something false about the person's own answers**, which is the same failure the security-gate reason had in round one:

- **The summary asserted an answer nobody gave.** The "none of these apply" card I added to close a round-one finding printed *"You told us none of the specific threads apply"* to someone who had never been asked — zero path rows existed. Two different facts had been collapsed into one sentence; the screen now distinguishes "you answered none" from "nothing asked you".
- **The provenance fix reached one surface of three.** The gate screen said "answered from your answers"; the summary and the rail still hardcoded "from your intake" for a fact derived from a gate the person answered themselves.

Root cause of the first, and the more useful finding: **one tick wrote a substantive answer for every other open area.** Autosave submitted the whole form, so ticking one box recorded a positive "none of these apply" against three questions nobody had touched — which then made the false summary sentence *technically* consistent with the database. Autosave now writes only areas the person has touched; submitting the form, which is an explicit act covering every question on screen, still writes them all.

Also from that round: the forward control was disabled during an autosave and swallowed the press silently (§24.3); a non-retryable refusal said "reload" while offering "go to my assessments"; the empty-state header contradicted the empty state on the same screen; the validator hole was closed for one shape only — a rule naming a gate that does not exist, or reading `paths` from a gate pre-fill where paths are not yet resolved, still validated clean and silently never fired.

## Agentic opportunity

**Registered today, not built (§22.1):**

- *Instrument contradiction lint — semantic half.* Rules that cannot both be
  satisfied, and questions that mean the same thing in different words, are
  judgement. It reports findings to a human and never edits the instrument
  (§8). The **structural** half — unsatisfiable conditions, cycles, chained
  derivations, unreachable options, rules naming things that do not exist —
  is deterministic and went into the validator, which is where the B3 and N7
  findings put it.
- *Plain-language term help on demand.* The honest answer to "(RAG)" on a
  business-user surface: grounded in a named policy or standard, quoted
  rather than paraphrased, and silent where it has no source.

Deliberately **not** agentic: the condition renderer FR-5 asks for. A
provenance sentence is what an auditor reads to understand why a question was
asked; generating it with a model makes it non-reproducible, and
non-reproducible provenance is worse than none. It is a pure function over
structured data and must stay one.
