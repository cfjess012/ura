# UAT — S1 · Intake

**Done when:** Create a project, complete intake, close the browser, reopen: everything is there. Owner reviews before S2.

Every requirement this slice owns gets a row below. Fill each one with what
was actually done and actually observed — "works" is not evidence. A row

### FR-1 — Structured intake in four ordered sections with conditional fields (hasValue · equalsAny · includesAny)

- **What was done:** Created a project through the UI and worked all four sections (Description, Ownership, Categorization, Compliance & Data), exercising each of the three conditional kinds.
- **What was observed:** "Other Business Units Involved" stayed hidden until a business unit was typed, then revealed with "Shown because a responsible business unit was entered." "What does the AI do?" revealed only on `Yes` (equalsAny). "Data Elements" revealed only after Internal/Confidential/Restricted was selected (includesAny). All eighteen fields render from `src/lib/intake.ts`; no question text exists in any component.
- **Result:** pass
- **Evidence:** `e2e/intake.spec.ts` asserts every reveal against the rendered DOM and passes headless; `test/unit/intake.test.ts` pins the exact field set per section so no field can be added or dropped silently.

### FR-2 — Projects persist and resume; intake is the project's identity record

- **What was done:** Completed intake, closed the browser page entirely, opened a new page cold at each section URL.
- **What was observed:** Every value returned — free text, the date, both selects, the multi-selects, and the conditional fields (which re-revealed because their triggers persisted). The project list showed the project by name.
- **Result:** fail
- **Corrected 2026-08-21, after independent verification:** The observation above holds only for the journey that was walked: sections completed in order, front to back. Completed out of order, saving any section erased every multi-select answer in the other sections and reported success (F1, blocking). "Projects persist and resume" was therefore claimed on a path, not on the requirement.
- **Follow-up (done 2026-08-21):** `intakePatchFrom` now writes only the fields a submission declares (G-28); the unit test that had asserted the defect as correct was replaced with three that pin the rule; `e2e/intake.spec.ts` gained a journey that answers the LAST section first and then saves an earlier one. Re-verified green.
- **Evidence:** `e2e/intake.spec.ts` closes the page and re-reads each section on a fresh page; `test/integration/db.test.ts` round-trips a record through real SQL applied to in-process Postgres, including a null launch date and multi-select arrays.

### FR-28 — A field marked required is enforced, server-side as well as in the form

- **What was done:** Started an assessment and clicked the forward control through all four sections answering nothing; then reached `/assess/third-party` directly by URL with an empty record.
- **What was observed:** Before the repair, four clicks landed on the risk areas with every intake column empty and no gate pre-filled. After it: the form stays on Description, names the three missing answers, marks three controls `aria-invalid`, focuses the first, and the live region reads the list; whatever was typed is still saved. The URL route to the risk areas redirects back to the first incomplete section and says why. This requirement did not exist when S1 was signed off — it was added after the owner walked past the gap in ten seconds (G-37).
- **Result:** pass
- **Evidence:** `e2e/intake.spec.ts` drives the blast-through and asserts the refusal, the focus, the live-region text and that typed answers survive; `test/unit/intake.test.ts` pins completeness and the section to return to; the redirect is a server component, so the form is not the enforcement point.

### NFR-5 — AWS-ready by construction: the five §6.4 obligations

- **What was done:** Reviewed the slice against each obligation and encoded them as tests.
- **What was observed:** Both services build from the repo root; `DATABASE_URL` is the entire configuration surface and is read only in `src/lib/config.ts`; persistence is Postgres-only through plain SQL migrations; no dependency without an AWS-managed equivalent. Pure logic in `src/lib/intake-values.ts` imports no framework, driver, or environment.
- **Result:** pass
- **Evidence:** `test/unit/architecture.test.ts` fails the build if a logic module imports a framework, if anything outside the store touches the driver, if `process.env` is read outside config, or if a connection string is hardcoded.

## Findings

- **Should-fix (resolved in-slice):** checkbox groups had `<label for>` pointing at a non-existent id, leaving them with no accessible name. Fixed with `aria-labelledby`; the E2E now depends on the group being findable by its label, so a regression fails the suite.
- **Should-fix (resolved in-slice):** saving had no failure state — a dropped connection left the button pending forever. Now a typed result, a plain sentence, a quotable reference, and the person's input preserved. Proven by taking the browser offline mid-save.
- **Note:** the owner's review replaced most of the intake question set (G-10) and removed one question entirely (G-20). Those are instrument changes, recorded in the governance log, not defects in this slice.

## Agentic opportunity

**Registered, not built:** *Intake quality assistant* (§22.1) — grades the
description against a published rubric and asks for the specific thing that
is missing, rather than accepting a sentence nobody downstream can use.

Deliberately **not** agentic: conditional field visibility and required-field
enforcement. Both are rules with one correct answer, and both are what every
later tier reasons from — a probabilistic answer there would be a guess
wearing the clothes of a fact.
